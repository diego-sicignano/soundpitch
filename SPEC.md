# SoundPitch — Specification

**SoundPitch lets a blind or low-vision fan follow a football match by ear.** It turns a stream of synthetic match events into a timed audio-description track, a spatial "ball sound", and captions. Built for the Microsoft x Premier League "Inside the Game" hackathon. The spec is the authority; code follows it.

## §1 Why

- Live audio description of football is rare and mostly volunteer-run; broadcasters have only just started (Sky Sports, 10 Oct 2026: about 109 Premier League games a season).
- Good description *describes the action* in a radio style, without opinions (RNIB guidance), and must fit into the gaps of play.
- Fans also want to know where the ball is and who is attacking.

## §2 Pipeline (the five hackathon stages, plus verify and context)

| Stage | Component | Kind |
|---|---|---|
| Ingest | `match_gen` synthetic match, 1 event every 3–9 s | code |
| Interpret | `moments` groups events into prioritised **moments**; `stats` counts the match statistics (§18) | code |
| Explain | `Describer` writes a `full` and a `short` sentence per moment | LLM (Foundry) or templates |
| Verify | `verifier` checks every name, number and attribution against the events; 2 retries, then the template fallback | code |
| Context | `stakes` adds one sentence on what the score now means to a goal, half-time or full-time cue, after verification (§5, Stakes); `recap` writes the summary of the match so far (§19) | code |
| Analyse | the **Analyst** agent writes three or four studio points, each citing its source; `analysis` checks every name and number against that source; a second attempt, then points written by code (§20) | LLM (Foundry, with the MCP tools of §16) or code |
| Render | `timing` plans cues into the silence between moments; `render` emits cues, earcons and WebVTT | code |
| Personalize | `Profile`: detail, language, sonification, calm mode, speech rate, a player to follow (§17), output channel | code |

Only code decides **what is true** and **when it is said**. The model only chooses words.

## §3 Data

- Pitch: `x` 0–100 along the length as the TV camera sees it (0 = left goal), `y` 0–100 across. Home attacks left to right in the first half, right to left in the second.
- `lane` is team-relative: `left`, `centre`, `right` from the point of view of the team attacking.
- `progress` of a team = `x` if it attacks left to right, else `100 - x` (0 = own goal line, 100 = opponent's goal line).
- Teams: `Northgate Red` (`home`), `Harbour Blue` (`away`), 11 fictional players each. Minutes are `t // 60 + 1` (1..90); no stoppage time.
- Storyline for `SEED = 424242`: goals by home at 16', away at 52', home at 78'; final score `Northgate Red 2 - 1 Harbour Blue`. Random play never scores.

## §4 Moments and detail levels

| Priority | Moments |
|---|---|
| 3 (must say) | kickoff, goal, half-time, full-time |
| 2 | shot (on, off, blocked), save, corner, dangerous free kick (`progress >= 70`), score reminder every 10 minutes |
| 1 | tackle/interception won in the opposition half or midfield, foul, throw-in, build-up reaching `progress >= 60` |
| 0 | any other run of passes/dribbles |

Detail profile → minimum priority: `essential` 2, `standard` 1, `full` 0. A run of consecutive pass, dribble, long ball and clearance events by one team is one **build-up** moment, described when it ends.

## §5 Describing and verifying

- Style: present tense, factual, no opinions, surnames only, team names, direction words relative to the attacker (`left`, `centre`, `right`).
- A `Description` has `full`, `short` and `refs`: a list of `(event_id, field, value)` claims. The `refs` are the audit trail of the facts a sentence may state: the code derives them from the moment (`describer.facts`) and a describer cannot add, drop or change them.
- The verifier rejects a description when any of these holds:
  1. `moment_id` or `lang` differ from the moment's and the profile's, or the `refs` differ from the ones the code derives.
  2. A ref differs from the event; the text names a player not involved in the moment; the text contains an integer that is not a score, the minute or a score reminder minute; `full` has more than 45 words or `short` more than 15 words or `short` is longer than `full`; `full` or `short` has more than 400 characters (the most `/api/tts` speaks), or a word count by whitespace or by words exceeds the limit. (The checks of S3, plus the length cap.)
  3. *Grounding.* A sentence may state only the facts the refs carry, plus the score. `describer.facts` builds them and drops the team, player or lane of the moment's last event when the moment's refs do not carry it (a save, a foul or a score reminder has no lane to state). Facts that carry a relation are written only as **canonical phrases**, built by code and copied verbatim: the score (`Northgate 1, Harbour 0`), the assist clause (`set up by Adeyemi`, `assist di Adeyemi`), the build-up chain (`Moretti, Okafor, Duval`), the minute phrase of a score reminder (`Minute 10`), the direction and zone phrases, and, where the refs carry a lane, the lane phrases (`from the left`). Outside canonical phrases every word of `full` and of `short` must be the surname of the player or the short name of the team the facts carry, a word of the **vocabulary** of the moment's template key (the words of that key's templates in `LEX`, `describer.py`; a hyphenated word may be written with a space, `half time`, but its parts are not words of their own), or an article or "and" (`the a an and`; `il lo la i gli le un una e`), the only words shared by every key. Every word that relates two facts, such as `for`, `on`, `by`, `per`, `di`, belongs to the templates of one kind of event, because "scores on Northgate" and "scores for Northgate" are different facts; a wider shared list was tried and reversed after review (D9). A digit is allowed only inside a canonical phrase. Text is compared after Unicode NFC normalisation and lower-casing. Another name, a number word, another team, a lane, zone or direction word, an event word of another kind, or an opinion is therefore rejected.
  4. Outside canonical phrases, a character other than a letter, whitespace or one of `. , ! : ; ' -` is present: symbols, emoji, `?`, quotes, brackets, control and invisible characters are rejected.
  5. The text does not say what happened: it has no outcome word of the key (a word that only this kind of event uses, so `time`, `off`, `Fine` or `shoots` alone are not enough), unless it is a score reminder carrying the score phrase.
  6. *Position.* A name or a canonical phrase stands only where a template of the key stands it. Ignoring articles, the word before it and the word after it must each be a word that comes before, or after, that name or phrase in some template of the key; the start of the text, its end and another canonical phrase all count as one *edge* neighbour, because phrases are optional. "Foul by Costa of Harbour" is a template order; "Foul of Costa by Harbour" is not, and neither is "Goal! Northgate finds Marsh" or "Corner to Rossi, taken by Harbour". A key whose templates never name the team, or the player, or never contain a phrase, does not allow it: a shot sentence carries no score, the score phrase (it starts with the home team) cannot stand where a team belongs ("Throw-in to Northgate 0, Harbour 0"), and the assist clause cannot be a subject ("set up by Adeyemi scores for Northgate").
  7. A required fact is missing: goal: scorer, team and score in `full`, scorer in `short`; kick-off: the team; half-time, full-time and score reminder: the score in `full`.
- A verifier that cannot run rejects: if the check raises, the pipeline counts the attempt as rejected (fail closed). A describer's result is copied into a plain, validated `Description` before it is checked, and only the copy can become a cue, so an object that answers differently each time it is read cannot pass and then change. The template fallback must verify; if it does not, building the session fails instead of speaking.
- What this guarantees and what it does not. Every entity, number, score, minute, lane, zone, direction and event outcome in a description comes from the moment's own facts, and the words around them come from a reviewed list. It does **not** verify the meaning of the prose. Names and phrases are held in the places the templates give them, but a describer can still reorder the allowed words that do not touch a name, or choose, among the words of the key, one that fits the sentence badly. For example "Foul of Harbour." (a foul by a Harbour player, worded like a foul against Harbour) is accepted, because "of" before the team is a template word and the rule looks one word to each side; looking two words back closes it but, measured on the corpus written with the word list in hand, accepts a third fewer sentences in English (46.8% to 33.0%) and a fifth fewer in Italian (78.7% to 62.8%), so it is not applied. `POST /api/tts` speaks only text the server itself returned as the `text` of a cue in a session (§8), so it cannot be used to synthesise other text; the 400-character cap is the length of the longest verified description. Adding a word to the vocabulary or to the shared articles is a human review decision (the word must not change a fact or a relation). The guarantee is bounded by the vocabulary, not by understanding the sentence.
- A false rejection costs only naturalness, because the verified template fallback exists; a false acceptance costs trust. When in doubt the verifier rejects.
- Attempt 1..3: failed moments get `ValidationFeedback` and are described again (max 2 retries); then the deterministic template description is used and the cue is marked `fallback`.
- Languages: `en` and `it`. The verifier is language-independent.

### Stakes: why the moment matters (S31)

A goal, the half-time whistle and the final whistle carry a **context sentence** that says what the score now means. It is written by code, never by a model, from the score state alone, and it is added **after** verification, so the verifier, the prompt, the recorded Foundry replies and their keys (§11) are untouched.

- *Source of the facts.* The moment's last event (`Event.team`, `Event.home_score`, `Event.away_score`: the score *after* the event, as the sentences above already state it) and, for a goal, the event before it (`id - 1`), whose score is the score before the goal. There is **no** context when the scorer is unknown, when a score before the goal would be negative, or when the event before the goal is present and its score is not the goal's score minus the goal: an inconsistent or unknown state is never guessed.
- *Goal.* Let `trailed` be how many goals the scorer's side was behind by before scoring (negative when it was ahead). Both sides on 0 before the goal: the opening goal of the match. Otherwise `trailed == 1`: level; `trailed == 0`: the scorer takes the lead; `trailed < 0`: it extends its lead; `trailed >= 2`: it pulls one back. One fixed phrase for each, per language: `The opening goal of the match.`, `That makes it level.`, `{team} take the lead.`, `{team} extend their lead.`, `{team} pull one back.`; `È il primo gol della partita.`, `Il risultato torna in parità.`, `{team} passa in vantaggio.`, `{team} allunga.`, `{team} accorcia le distanze.` `{team}` is the short name of the scorer. The Italian uses the singular verb because a club name is one subject; the Italian *templates* of §5 keep their plural verbs after a club name (changing them would change the verifier's vocabulary and every recorded reply key), so the two registers differ slightly. The Italian was reviewed by the author, a native speaker.
- *Half-time.* Level: `All square at the break.` / `Parità all'intervallo.`; otherwise `{team} lead at the break.` / `{team} avanti all'intervallo.` with the side that is ahead.
- *Full-time.* Level: `The match ends level.` / `Finisce in parità.`; otherwise `{team} win.` / `Vince {team}.` A result is stated only by the full-time moment, never by a goal.
- *Nothing else.* Kick-off, shots, saves, set pieces, turnovers, build-ups and score reminders get no context. No sentence says anything about tactics, form, history, the future or any statistic the events do not hold.
- *Where it goes.* Only in the `full` text of a cue. `Cue.text` is the verified description, a space, then the context sentence; `Cue.context` holds the context sentence alone (`None` when there is none, and always for the `short` variant), so a page or a captioning system can tell code-written context from the description. The planner times the longer text; if only `short` fits, the cue has no context. The `Description`, its `refs` and the cue `status` are those of the verified description: the verifier did **not** check the context sentence and nothing claims it did. Its correctness rests on the tests of S31 and on the fixed phrases above.
- *Voice.* The sentence is part of the cue text, so the browser voice, the captions, the transcript, the screen-reader output and `/api/tts` (§8) treat it like any other text. A stored clip exists only for a text in the manifest; `clips_build` lists the texts with their context, and until clips are made the browser voice speaks it.

## §6 Timing

- Speech duration estimate: `words * 60000 / wpm + 300` ms, `wpm = 165 * rate` (`en`) or `155 * rate` (`it`).
- A cue may start no earlier than its moment time plus 300 ms, and not later than moment time plus the **max lag**: priority 3 → 10 s, 2 → 6 s, 1 → 5 s, 0 → 4 s.
- Cues never overlap; gap between cues at least 250 ms.
- Planning order: priority high to low, then time. For each moment try `full`, then `short`; if neither fits it is **dropped** with a reason. Priority 3 is never dropped: it takes the first free gap after its earliest start, even past the max lag.
- The session's `duration_ms` is the preset window, extended to the end of the last cue when a cue runs past it. The full-time whistle is the last event of its window, so its sentence always does: without the extension the player would stop before it is spoken. Every cue therefore starts and ends inside `duration_ms`, and no cue is counted that the player would not play.
- The result is deterministic.

## §7 Earcons (ball sound) and calm mode

One short sound per event, `pan = (x - 50) / 50` (left to right), `pitch = progress / 100` (higher near the opponent's goal). Kinds: `tick` (pass, dribble, long ball, clearance), `turnover`, `shot`, `save`, `goal`, `set_piece`, `whistle`, `whistle_long`. **Calm mode** keeps only `goal` and `whistle*` at gain 0.3 and slows speech to rate 0.9 at most.

| Method | Path | Result |
|---|---|---|
| `GET` | `/api/match` | teams, rosters, final score, goal list |
| `GET` | `/api/presets` | windows: `kickoff`, `goal_1`, `goal_2`, `goal_3`, `final_whistle` |
| `GET` | `/api/session?preset&detail&lang&earcons&calm&rate&focus&focus_team` | `Session`, with the match statistics of the window (§18) |
| `GET` | `/api/session.vtt?…` | WebVTT captions |
| `GET` | `/api/cuesheet?…` | `CueSheet`, JSON for graphics and captioning systems (§13) |
| `GET` | `/api/cuesheet.schema.json` | JSON Schema of the `CueSheet` |
| `POST` | `/api/tts` `{text, lang, rate}` | `audio/mpeg` from Azure AI Speech, `501` when not configured |
| `GET` | `/api/health` | `{status, llm}` |
| `GET` | `/api/voice` | `VoiceSupport`: `{stored_clips: {en, it}, live}`, what the Azure voice can do on this server (S29) |

Errors (`{code, message}`): unknown preset → `404 preset_not_found`; invalid parameter → `422` (also a `focus` without a `focus_team`, or the other way round, and a shirt that is not in that team); `/api/tts` → `501 tts_not_configured`, `403 tts_text_not_issued`, `502 tts_failed`, `429 rate_limited`; `/api/session`, `/api/session.vtt` and `/api/cuesheet` with `SOUNDPITCH_LLM=foundry` or `SOUNDPITCH_ORCHESTRATOR=workflow` and a missing setting or package → `503 llm_not_configured`; a `SOUNDPITCH_LLM` or `SOUNDPITCH_ORCHESTRATOR` value that is not a supported mode → `503 llm_not_configured` whose message names the setting and the supported modes and **never the value** (also on `/api/health`: a mistyped setting is not healthy, S32); an unhandled error → `500 internal_error` (a fixed message that names no setting and no value). `Session.cues[].start_ms` is relative to the window start.

### Response headers (S25)

Every response, an unhandled `500` included, carries `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` and `X-Frame-Options: DENY`. Every response except the interactive API documentation (`/docs`, `/redoc`, which load their own scripts) also carries `Content-Security-Policy: default-src 'self'; media-src 'self' blob:; img-src 'self' data:; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`. The page uses no inline script, no external request and no inline style attribute, so the policy needs no relaxation; the end-to-end suite fails if the browser reports a policy violation.

### `/api/tts` guard (S22) and stored clips (S26)

Order of checks: input validation (`422`), text not issued (`403`), the client's per-minute limit (`429`), a stored clip (`200`), Speech not configured (`501`), then the live limits (`429`), then Azure.

- **Only issued text.** The server remembers the `(lang, text)` of every cue, recap line (§19) and analysis point (§20) it has returned in a session (at most 4,096 pairs, oldest forgotten first, per process). Any other text is refused with `403 tts_text_not_issued` and nothing is spoken. The page then falls back to the browser voice. A server restart forgets the pairs; reloading the session issues them again.
- **Stored clips (none made yet).** `backend/app/audio/` holds one mp3 for each sentence the demo can speak, made once at speech rate 1.0 with the neural voices of §14, and a `manifest.json` (`version`, `format`, `voices`, `generated`, and for each clip its id, `lang`, `text` and size). `/api/tts` serves the clip of an issued `(lang, text)` with no Azure call and no Speech key, with the header `X-Audio-Rate: 1`; the page applies the speed itself (§9). A clip is used only if its manifest entry has the same language and text and its file exists and is not empty; otherwise it is treated as absent. The clips are made by `python -m app.clips_build`: without options it is a **dry run** that only counts the sentences, the characters and the estimated cost and needs no key and no network; `--generate` calls Speech (`AZURE_SPEECH_KEY`, `AZURE_SPEECH_REGION`), only for missing clips, refuses to send more than `--max-chars` (default 15,000) characters, accepts `--limit N`, retries `429` and `5xx` with a growing wait, stops at `401` or `403`, and never prints the key.
- **Live path (development only).** Without a stored clip and with Speech configured the text is sent to Azure. Repeating a request is served from memory (at most 256 clips, keyed by language, text and speech-rate percent), and the response carries `X-Audio-Rate` equal to the rate applied by the service. These requests are limited before Azure is called: requests per minute for the whole process (`SOUNDPITCH_TTS_PER_MINUTE`, default 120); characters sent to Azure per UTC day (`SOUNDPITCH_TTS_CHARS_PER_DAY`, default 60,000) and per UTC month (`SOUNDPITCH_TTS_CHARS_PER_MONTH`, default 300,000). Characters are counted when a request is sent, also if it then fails, because it may have been billed. A value that is not a whole number of at least 1 is ignored and the default applies.
- **Per client (S27).** At most `SOUNDPITCH_TTS_PER_CLIENT_PER_MINUTE` requests a minute (default 30) per client, counted for every request that passes the issued-text check. The client is the connection's address or, only with `SOUNDPITCH_TRUST_PROXY=1`, the address in the **last entry of the last `X-Forwarded-For` header line**, read defensively because proxies write it differently: `1.2.3.4`, `1.2.3.4:5678`, `[2001:db8::1]:5678`, `2001:db8::1` and `[2001:db8::1]` all give the address without the port, so a client that changes port is still one client; anything that is not an address falls back to the connection's address. With `SOUNDPITCH_LOG_FORWARDED=1` the server logs, for up to five distinct values, only the **shape** of the raw header (every digit replaced by `9` and every hex letter by `x`, so `999.9.999.9:99999`), never an address, so the format of a real proxy can be settled from the log stream.
- **What this is not.** The live counters live in the memory of one process and restart at zero; they are not a spending cap and not a statement about the Azure bill. The judges' image holds no Speech key, so it has no Speech spending at all; the pricing tier of a Speech resource is the only hard cap on a resource that is used live.
- **Availability (S29).** `GET /api/voice` says what the Azure voice can do on this server, so the page never offers a voice that is not there: `stored_clips` is, for each language, the number of manifest entries whose file is present and not empty (the same test as a clip is served by), and `live` is true when `AZURE_SPEECH_KEY` and `AZURE_SPEECH_REGION` are both set. It sends nothing to Azure, reads no key value and is not rate limited. A server without clips and without a key answers zeros and `false`: this is the state of the repository until the clips are made.
- **Disclosure.** The Azure voice is synthetic (Code of Conduct for Microsoft AI Services): the page says so in a visible note (§9).

## §9 UI (`frontend/`, plain HTML, one page, keyboard first)

Landmarks `header`, `main`, skip link. All controls are real labelled form elements. The controls are English; the commentary is in the language of the profile, so the transcript, the captions and the live region carry `lang` of the session (WCAG 3.1.2) and the page language stays `en`. The Azure voice is synthetic, so a visible note under the Voice control says so and describes it (`aria-describedby`). The page applies the speed of a stored clip itself: it plays the audio with `playbackRate` set to the effective speech rate divided by the `X-Audio-Rate` header of the response (pitch preserved); a response without that header is played as it is (S28). **The page offers only voices that exist (S29, S30).** It reads `/api/voice` when it loads and whenever the language changes: the `azure` option of the Voice control is disabled, and the note says so, when the server has no stored clip for the language of the commentary and no live voice; if `azure` was selected and the language changes to one without clips, the page goes back to `browser` and says so in `status`. The default voice is `azure` when the server holds stored clips for the language of the page when it loads, so the neural voice is heard without a setting; otherwise it is `browser`, the only one that needs nothing from the server. When Play is pressed with the browser voice and the browser has no speech synthesis, or no installed voice for the language of the commentary, `status` says so and points to the captions, the transcript and the “My own screen reader (text only)” output, which keep working; the page does not pretend that anything is being spoken. ## §10 Acceptance rows

| ID | Given | Then |
|---|---|---|
| **S1** | seed 424242 | identical output on two runs; ids sequential; times non-decreasing; goals at 16' home, 52' away, 78' home; final score 2-1; coordinates within 0–100 and lanes consistent with direction |
| **S2** | the match | every priority-3 kind is a moment at every detail level; `essential` ⊂ `standard` ⊂ `full`; build-ups are runs of one team's pass-like events |

| **S4** | scenarios | `bad_then_good`: every cue verified after one retry; `always_bad`: failing moments use the fallback, cues are marked `fallback`, track is complete |
| **S5** | the planner | no overlaps, gaps ≥ 250 ms, all priority-3 moments scheduled, high priority never dropped for low, `short` used when `full` does not fit, every cue ends inside `duration_ms`, deterministic |

| **S10** | evaluation harness | across 20 seeds and all detail levels: no overlap, 100% of priority-3 moments scheduled, 100% of planted errors caught |

## §11 Foundry describer (`SOUNDPITCH_LLM=foundry`)

- Settings: `FOUNDRY_PROJECT_ENDPOINT`, `FOUNDRY_MODEL`, and the cost limits of the last bullet (`SOUNDPITCH_LLM_CALLS_PER_MINUTE` 2, `SOUNDPITCH_LLM_CALLS_PER_DAY` 20, `SOUNDPITCH_LLM_TOKENS_PER_DAY` 120000, `SOUNDPITCH_LLM_EUR_PER_MONTH` 2.00, `SOUNDPITCH_USAGE_DB`). Authentication uses the default Azure credential (`az login` locally, a managed identity in Azure). No key in the code or the image. A missing setting, or a missing optional package, stops the request with `503 llm_not_configured` and a message that names it; the other modes need neither.
- Package: `backend/requirements-agents.txt` (Microsoft Agent Framework's `FoundryChatClient`, pinned; D10). The core `requirements.txt`, the tests and the offline modes never import it.
- One model call per attempt covers all pending moments of the window, in chunks of at most 20 (a reply of 20 moments is about 600 tokens; the output cap is 1,000). The call runs on one long-lived event loop owned by the adapter, so the client, its connection and its token are reused and never shared across threads or loops.
- The prompt holds the style rules of §5, the language, and for each moment only: its template key, the player's surname, the team's short name, the canonical phrases of §5 (score, assist clause, chain, lane, zone, direction, minute), the vocabulary of its key, the places a name or a phrase may stand (`verifier.position_contexts`), one or two example sentences made of those same facts, and, on a retry, the verifier's issues for that moment. Nothing else about the match: no other player, no other event, no refs.
- The reply is a JSON object `{items: [{moment_id, full, short}]}` (structured output with a Pydantic model; the text is parsed again whatever the SDK returned). The model never sends refs: the code attaches the refs of `describer.facts`. An item for an unknown moment, a duplicate, or a missing field is dropped; a moment without a valid item is a failed attempt for that moment, as is a reply that does not parse, a call that raises and a call that takes more than 20 s.
- Every wording passes through the pipeline's own verifier and retries (§5), unchanged: valid JSON or a conforming schema never makes a sentence verified.
- Cost guards, outermost first.
  1. *Azure.* The deployment's tokens-per-minute allocation (8,000): a **throughput** ceiling, not a spending limit. The service estimates a request as its prompt (from the characters) plus `max_tokens`, even if unused, and answers 429 above the allocation. And a budget of 5 EUR a month on the resource group, which only **alerts**: cost data arrives 8 to 24 hours late, budgets are evaluated every 24 hours, nothing is stopped. Neither is a cutoff.
  2. *The usage ledger* (`backend/app/usage.py`, SQLite, D11) decides before every model call. It lives in one file (`SOUNDPITCH_USAGE_DB`, default `backend/data/usage.sqlite`) and survives restarts and concurrent threads and processes on the same host. Per UTC period it allows at most `SOUNDPITCH_LLM_CALLS_PER_MINUTE` calls (default 2) in a minute, `SOUNDPITCH_LLM_CALLS_PER_DAY` (default 20) and `SOUNDPITCH_LLM_TOKENS_PER_DAY` (default 120,000) in a day, and an estimated spend of `SOUNDPITCH_LLM_EUR_PER_MONTH` (default 2.00) in a month; the environment may change these, but the monthly ceiling can never be set above 4.00, so it always sits below the 5 EUR budget. Before the call it **reserves** the worst case in one atomic step: the prompt estimated at one token per two characters, the full 1,000 output tokens, three SDK attempts, at the list price **in US dollars** (gpt-4.1-mini Global Standard on 2026-10-20: 0.40 per million input tokens, 1.60 per million output) **counted 1:1 as euros** (a stated policy, not a market rate: it over-counts while a dollar is worth less than a euro) plus a 25% margin, so 0.50 and 2.00 per million tokens. After the call it replaces the reservation with the usage the service reports. A call that fails, times out or is cancelled keeps its worst-case reservation, because it may have been billed (a call that timed out is settled with the usage the service reports if its answer arrives later); only a call that never left the process is released. Reservations in flight count. If the database cannot be opened, read or written, the call is refused (fail closed).
  3. *Per request.* At most 1,000 output tokens, 20 moments, an estimated prompt of 12,000 tokens, 2 calls in flight.
  A refused call never reaches Azure: the chunk is described by the template describer, the trace says `llm budget exhausted: templates (reason)` and the log gets one line without secrets. Replies that parse are kept in the same database (key: match seed, language, attempt, the moments, the issues sent, a hash of the instructions), so a window asked once is never paid for again, across restarts; identical requests in flight share one call. The API keeps a session only if no model call failed and no budget was exhausted while building it.
  What this does **not** guarantee. The ledger is per host: replicas, or a container disk that is replaced at each deployment, neither share nor keep it (a hosted copy would need one replica with a persistent volume). The estimate is only as good as the price and the token estimate; Azure bills what it processed, which the application sees only through the usage it reports. There is no spending cutoff in Azure for pay-as-you-go: an automatic stop would have to be built (a budget action group calling a function that deletes the deployment) and was not.
- Evidence against the real service: `python -m app.foundry_run --write` runs every preset at every detail level in both languages and writes `docs/evidence/foundry-run.md` (date, model name, first-attempt pass rate, retries, fallbacks, rejection reasons, median and p95 call latency). Without settings it exits 2 and says which are missing.

### Replay mode (`SOUNDPITCH_LLM=replay`), the judges' path (D12)

- The public demo must work for any judge, free and without restriction (rules 4.8), without a live model call and without a datastore. `replay` answers a request with the reply Foundry gave to the *same request* earlier, read from `backend/app/replay_data/foundry_replies.json` (`{version, model, recorded, replies: {key: reply}}`). The key is the one of the reply cache above (match seed, language, attempt, moments, issues, instructions), so a changed prompt, a new window or a retry with new issues has no recorded reply.
- A recorded reply is data, not a verdict. It becomes `Description`s with the code's refs, like a live reply, and the pipeline's verifier checks every session, so a stale, edited or hostile record ends in the template fallback. A request with no recorded reply, and a missing, invalid or unparsable file, are described by the templates and the trace says `no recorded reply: templates`; nothing fails.
- The file is made offline from the replies a live Foundry run stored in the usage ledger: `python -m app.foundry_run` (billable, with the raised limits of §11), then `python -m app.replay_export --db <ledger> --model <model> --recorded <date>`; `python -m app.replay_export --check` reports how many requests (preset x detail x language, first attempt) the file covers. Nothing in the replay path contacts Azure, imports the SDK, or writes a file, so it runs as the non-root user of the container and on a read-only file system.
- What it is not. It is not a live model: the words are those of one recorded run, and the evidence of how that model fares is `docs/evidence/foundry-run.md`.

## §12 Agent Framework workflow (`SOUNDPITCH_ORCHESTRATOR=workflow`)

The describe, verify, retry, fallback and timing flow of §5 and §6 is also expressed as a Microsoft Agent Framework workflow: a graph of executors with a conditional retry edge. It builds the same `Session` as the plain pipeline; it adds an orchestration that can be drawn, traced executor by executor and extended, not new behaviour.

| Executor | Kind | Role |
|---|---|---|
| `MomentDetector` | code | the window's events to moments |
| `Describer` | the profile's describer: templates, or a model on Foundry (§11), or recorded replies | pending moments and the verifier's feedback to descriptions; a describer that raises costs an attempt |
| `Verifier` | code | accepts descriptions, or keeps the moments pending with the issues as feedback |
| `Fallback` | code | the verified template description of the moments still pending after the last attempt |
| `TimingPlanner` | code | cues, earcons, ball track and the report; the workflow's output is the `Session` |

Edges: `MomentDetector -> Describer -> Verifier`; `Verifier -> Describer` while moments are pending and attempts < 3 (a conditional edge carrying the feedback); `Verifier -> Fallback` when moments are pending and the attempts are used up; `Verifier -> TimingPlanner` when nothing is pending; `Fallback -> TimingPlanner`; then `TimingPlanner -> Analyst -> AnalysisChecker`, and `AnalysisChecker -> Analyst` once when a point was rejected (§20). The `AnalysisChecker` yields the session.

- `plain` (default) keeps the dependency-free pipeline. `workflow` needs `agent-framework-core` (`requirements-workflow.txt`, also part of `requirements-agents.txt`) and answers `503 llm_not_configured` naming the package when it is missing. **The judges' image runs `workflow`** with the recorded replies (D31), so the demo is the Agent Framework graph and its trace names each executor; the page shows the executor beside each pipeline step. The Agent Framework version is pinned (D10, D13).
- The messages between executors are immutable (a frozen dataclass copied at each step): edge conditions are evaluated when a message is delivered, and a message changed by the executor that sent it would make the wrong edge fire (found with the installed version, D13).
- For the same describer both orchestrators return the same cues, statuses and report (`Session.trace` differs: each step of the workflow names its executor in `TraceStep.executor`; the plain pipeline leaves it empty).
- What it is not. The model is not an autonomous agent with tools: code decides what is true and when it is said (§5), so only the `Describer` touches a model and the other executors are deterministic code. The workflow does not make the answers better; it makes the control flow explicit.
- Selection is by the environment at request time. It applies to `/api/session`, `/api/session.vtt` and `/api/cuesheet` alike.

## §13 Cue sheet (machine-readable output)

`GET /api/cuesheet?preset&detail&lang&earcons&calm&rate` returns a `CueSheet`, JSON, for a graphics or captioning system. It is the `Session` of the same parameters (§8) in a flat, versioned shape; it is built from the session, so it carries the same verified words and the same timings.

- Fields: `schema_version` (1), `preset`, `lang`, `match_clock_from` (`mm:ss` of match time at the window start), `duration_ms`, `items`.
- `items` are sorted by `at_ms` (relative to the window start), then `audio_description`, `caption`, `ball_sound`, then `id`. Every item has `id` (a string, unique in the sheet), `type` and `at_ms`.
  - `audio_description` and `caption` add `duration_ms`, `priority` (0..3), `event_ids`, `text`, `status` (`verified` or `fallback`) and `context` (optional, the code-written context sentence that ends `text` when there is one, §5 Stakes; a compatible addition). A `caption` has the same `at_ms`, `duration_ms` and `text` as its `audio_description`; the two items of one cue have ids `ad-{cue id}` and `cap-{cue id}`.
  - `ball_sound` adds `sound` (the kinds of §7), `pan` (-1..1), `pitch` and `gain` (0..1). It has no duration: the player decides how long a sound lasts.
- `audio_description` items never overlap one another.
- The JSON Schema is served at `GET /api/cuesheet.schema.json` and committed as `docs/contracts/cuesheet.v1.schema.json`; both are generated from `contracts.py` (`python -m app.cuesheet --write docs/contracts/cuesheet.v1.schema.json`). The schema is a discriminated union on `type` and forbids unknown fields. The sheet is validated with the Pydantic models that generate the schema; no second validator is a dependency.
- Compatible changes only add optional fields. Any other change increments `schema_version` and the schema file name.

## §16 MCP server (S17)

`python -m app.mcp_server` serves the match to any MCP client (GitHub Copilot agent mode, an Agent Framework agent, others) over stdio, with the official MCP Python SDK (`mcp` 1.30.0, FastMCP, pinned in `requirements-mcp.txt`; the judges' image includes it, D32). The tools are read-only and return the contract objects of `contracts.py` as structured JSON:

| Tool | Result |
|---|---|
| `list_presets()` | the windows, `list[Preset]` |
| `get_match()` | teams, rosters, final score and goals, `MatchHeader` |
| `get_moments(preset, detail="standard", focus=None, focus_team=None)` | the window's moments with priorities (§4, §17), `list[Moment]` |
| `get_commentary(preset, detail="standard", lang="en", focus=None, focus_team=None)` | the session's verified cues and its report, `Commentary {preset, lang, cues, report}`, built by the same pipeline, orchestrator and describer as `/api/session` |
| `get_stats(minute)` | the match statistics of §18 from kick-off to the end of that minute (1..90), `MatchStats {minute, home, away}` |
| `get_events(preset)` | the window's synthetic events, as ingested, `list[Event]` |
| `get_recap(preset, lang="en")` | the code-written summary of the match up to the window's end (§19), `Recap` |

One prompt, `match_report(preset, lang="en")`, asks the client's model for a short report built only from `get_recap`, `get_stats` and `get_commentary`, quoting their sentences and numbers as they are.

An unknown preset is a tool error whose message starts with `preset_not_found`; a `focus` without its team, a shirt not in that team or a minute outside 1..90 is a tool error starting with `invalid_parameter`; an unknown detail or language is refused by the tool's input schema. The server writes nothing to standard output except the protocol. An agent that answers questions through these tools gets only sentences the verifier accepted and numbers counted by code: the tools add a way in, not a new source of facts.

## §17 Player and club focus (S18)

`Profile.focus_team` alone follows a **club**; with `Profile.focus`, a shirt number of that side, it follows one **player**. A shirt without its side is refused. With a focus, moments that involve it (an event of the moment whose `team` is `focus_team` and, for a player, whose `player` or `target` is `focus`; score reminders never count) have their priority raised by one, up to 2 (priority 3 stays reserved for must-say moments), before the detail filter, so the player's turnovers and build-ups reach `standard` and their passes reach `essential` when they lead to a priority-1 moment. Their earcons (the events of the club, or of the player as actor or receiver) have gain x1.5, capped at 1.0, also in calm mode. Descriptions do not change. Without a focus nothing changes. A shirt that is not in that team, or a shirt without `focus_team`, gives `422`. The page offers both clubs and their players in a `focus` select (§9). A changed set of moments is a request with no recorded reply, so in replay mode the templates describe it, verified, and the trace says so (§11).

## §18 Match statistics (S33)

Code counts a few broadcast statistics from the events, for the listener who wants numbers as well as the story. No model writes them and no sentence speaks them: they are shown in a table on the page and sent with the session. They are per team and counted **from kick-off** to the moment shown (the match so far), not only inside the window.

- `passes`: the team's `pass` and `long_ball` events. `possession`: the team's share of all passes so far, in whole percent; the two teams add up to 100, and both are 50 before the first pass. A share of passes is the usual broadcast estimate of possession; the events carry no ball-in-play time.
- `passes_completed`: a pass whose next event with a team, a `foul` aside (the fouling side is the other team and the passer's side keeps the ball), belongs to the same team. That event *resolves* the pass; a pass still open at the half-time or full-time whistle is never resolved. `pass_accuracy`: completed passes over resolved passes, in whole percent; 0 when none is resolved.
- `avg_pass_m`: the mean straight-line length of the team's passes, in metres, from the position of the event before the pass to the pass's own position (an event's position is where the ball ends up), with `x` scaled to 105 m and `y` to 68 m, rounded to one decimal; 0 when there is no pass.
- `recent_possession`: the same share over the passes of the last five minutes of match time before the point (300 s, from the time of the last event counted), 50 each when there is none: it shows which side is pressing now, which the share since kick-off hides.
- `shots`: `shot_on_target`, `shot_off_target`, `shot_blocked` and `goal`; `shots_on_target`: `shot_on_target` and `goal`; `ball_won`: `tackle` and `interception`.
- `Session.stats` is a list of `StatsPoint {t_ms, home, away}`: the first at `t_ms = 0` with the counts before the window, then one for each event of the window, at the event's time relative to the window start, with the counts after it. The page shows the last point whose `t_ms` is not after the clock. Deterministic.

## §19 Match recap (S34)

Code writes a short summary of the match up to the end of the window, for a studio or a listener who joins late. No model writes it and the verifier does not check it: every sentence is a fixed phrase filled from the events, like the score context of §5, so it carries only names, minutes and numbers the events hold. `Session.recap` is a `Recap {preset, lang, minute, lines}`; the MCP tool `get_recap` returns the same.

- *The score.* After a full-time event in the window: `Full-time: Northgate 2, Harbour 1.` / `Finale: Northgate 2, Harbour 1.`; otherwise `After {m} minutes: Northgate 1, Harbour 0.` / `Dopo {m} minuti: Northgate 1, Harbour 0.`, with `m` the minute of the last event up to the window's end. Before any goal the score line is the only goal-related line.
- *Each goal so far, in order.* `Minute {m}: {scorer} scores for {team}, set up by {assister}.` / `Minuto {m}: gol di {scorer} per {team}, assist di {assister}.`; the assist clause only when the event before the goal is a pass of the same team whose receiver is the scorer (§4). Then, when the scorer's side had at least 60% of the passes in the five minutes before the goal (`recent_possession` of §18, counted up to the event before the goal): ` {team} had {p}% of the passes in the five minutes before.` / ` {team} aveva il {p}% dei passaggi nei cinque minuti prima.`; at most 40%: ` It came against the run of play: {team} had {p}% of the passes in the five minutes before.` / ` È arrivato controcorrente: {team} aveva il {p}% dei passaggi nei cinque minuti prima.`; nothing in between.
- *The numbers.* `Possession: Northgate 53%, Harbour 47%. Shots: 16 to 18, on target 7 to 8.` / `Possesso: Northgate 53%, Harbour 47%. Tiri: 16 a 18, nello specchio 7 a 8.`, from §18 at the window's end.
- The page shows the summary when the clip has finished, in the language of the session, and not before (it would tell what is about to happen). Deterministic.

## §20 Analyst agent (S35)

A second agent, with its own role, reads the finished session and writes **three or four studio points** about the window: what decided it, who pressed, what the numbers say. Code checks every point before anyone hears it.

- *Sources.* Each point cites exactly one source by id: `recap:{n}` (line `n`, from 1, of the recap of §19) or `stats:{m}` (the statistics of §18 at the end of minute `m`, 1..90, written as one sentence per team: `Minute 45. Northgate: possession 53%, last five minutes 60%, passes completed 123 of 147, pass accuracy 84%, average pass 14.8 m, shots 10, on target 5, balls won 32.`). The same facts are what the MCP tools `get_recap` and `get_stats` return; `get_commentary` gives the agent the described moments as context, but a cue is not a source, because the cues change with the detail level, the language and the focus while the recap and the statistics depend only on the window. So one recorded analysis serves every profile of a window and language.
- *The check (`analysis.check_point`).* A point is rejected when its source does not exist; it has more than 40 words or 300 characters; it holds a character other than letters, digits, whitespace and `. , ! : ; ' - % ( )`; a player surname or a team name (short or full) in it does not appear in its source; a number in it (an integer or a decimal, a `%` aside) does not appear in its source; or it states no name and no number at all (an opinion with no fact). A point that speaks of pressure or dominance (a word starting `press`, `domin`, `predomin` or `control`) must cite a line that holds a share of passes (a `%`), so a judgement about who was on top rests on a number. A point that cites `stats:{m}` must name exactly one team, and its numbers (the minute aside) must be in that team's sentence, so a number cannot be given to the wrong team. Names and numbers are compared as whole words after lower-casing. What it guarantees: every name, number and minute in a point comes from the line it cites, so a scorer cannot be swapped with another line's scorer, nor a minute with another goal's. What it does not: the judgement around those facts ("dominated", "against the run of play"), nor which team a number belongs to inside a recap line that names both teams.
- *Attempts.* Attempt 1 asks for points. When a point is rejected, attempt 2 asks again with the issues. The points that passed (at most four, the first attempt's first) become `Session.analysis` with `status: verified`. When none passed, code writes the points (`CodeAnalyst`: the goal lines and the numbers line of the recap, cited as `recap:{n}`) and `status` is `fallback`.
- *Contract.* `Analysis {by, status, attempts, rejected, points: [AnalysisPoint {text, source}]}`, `by` is `model` or `code`, `rejected` counts the points the check refused. The trace has an `analyst` step per attempt and an `analysis_check` step per check.
- *Analysts, by `SOUNDPITCH_LLM`.* `scripted`: `CodeAnalyst`. `bad_then_good`: a flawed analyst once (it swaps a scorer for another line's scorer), then `CodeAnalyst`. `always_bad`: always flawed, so the fallback speaks. `replay` and `foundry`: recorded replies of the Foundry Analyst, read from `replay_data/analyst_replies.json` and checked on every session like any other reply; a request with no recorded reply gives the fallback.
- *The live Analyst.* `python -m app.analyst_run` (billable, behind the ledger of §11) runs a Microsoft Agent Framework `Agent` on Foundry whose tools are the MCP server of §16, started as a stdio subprocess (`MCPStdioTool`), asks it for every window and both languages, checks the points, and writes the recorded replies and the tools each run called. The judges' path never calls it. The reply key covers the match seed, the window, the language, the attempt, the issues sent, the instructions and the recap lines, so a changed recap is asked again, not served stale.
- *Page.* After the summary of §19, when the clip has finished: the points, under "Studio analysis", with a line `Written by an AI agent on Microsoft Foundry; every name and number was checked against the line it cites.` (or `Written by code from the summary.` for `by: code`), and read aloud after the summary.
